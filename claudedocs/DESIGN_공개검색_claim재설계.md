## 1. 현황 정밀 기술 (코드 근거)

### 1-1. 공개 검색 엔드포인트 3종 — 인증 없음, rate limit 없음

`services/account/app/auth/router.py`의 `/auth` prefix 하위, **인증 데코레이터/의존성 없이** 노출된다. `server.py`에는 `slowapi` 등 어떤 rate limiter도 등록돼 있지 않다(전체 코드베이스 grep 결과 `slowapi|rate_limit|Limiter` 매치 0건).

| 엔드포인트 | 라인 | 파라미터 | 반환 필드(마스킹 없음) |
|---|---|---|---|
| `GET /auth/public/player-search` | 228-272 | name, birth_year, team, weapon, league | `players`에서 `id, player_name, team_name, birth_year` + 조인으로 `weapons[], leagues[]` |
| `GET /auth/public/child-search` | 275-316 | name, birth_year, team, weapon, league | 동일 (`id, player_name, team_name, birth_year` + `weapons[], leagues[]`) |
| `GET /auth/public/org-search` | 319-342 | name | `organizations`에서 `id, name, org_type, province, city` |

- 반환 SELECT는 `router.py:250-252`(player), `295-297`(child), `332-334`(org)에 명시.
- 무기/리그 주석: `_annotate_and_filter_by_weapon_league`(147-221)가 `rankings→events` 조인으로 `weapons`, `leagues`를 후보에 덧붙인다(라인 217-218). 즉 응답에는 **실명 + 출생연도 + 소속팀 + 종목 + 연령대(리그)** 가 함께 나간다.
- 최소 쿼리 조건: 이름 2자 이상(라인 243). 그 외 제약(로그인·토큰·호출 빈도) 없음.

**미성년 노출 문제(P1-2):** `players`에는 초·중등부 선수가 포함되고, 검색은 이들의 실명+출생연도+소속을 그대로 반환한다. 프론트(`register.html:808-814`)는 "중등부 이하로만 확인되는 선수"를 **선택 버튼만** 비활성(`보호자 계정 필요`)할 뿐, **검색 응답 자체(이름/생년/소속)는 그대로 화면에 렌더**된다(`register.html:871-898`). 서버는 미성년 여부와 무관하게 전부 반환한다.

### 1-2. register.html이 실제로 의존하는 필드 (프론트 영향 파악)

`services/account/templates/auth/register.html` grep 결과:

| 사용 위치 | 의존 필드 | 용도 |
|---|---|---|
| `_renderPlayerResults` 872-879 | `player_name`(또는 `name`), `team_name`, `birth_year`, `weapons[]`, `leagues[]` | 결과 카드 표시(이름/상세/배지) |
| `isMinorLeaguePlayer` 811-813 | `leagues[]` | 미성년 리그 게이팅 판단 |
| `selectPlayer/selectChild` 914-951 | `id`, `name`, `team`, `birth_year` | 히든 필드(`selected_*`)에 저장 |
| `searchOrgs` 973-982 | `id`, `name`, `org_type`, `province`, `city` | 조직 카드 표시 |

→ **프론트가 반드시 필요로 하는 것:** 후보를 사람이 식별할 최소 정보(`id`, 이름, 소속, 연령대/무기 배지)와, 미성년 게이팅을 위한 `leagues`. **`birth_year`(정확한 출생연도)** 는 카드에 "YYYY년생"으로 표시하는 데만 쓰이며(라인 875), 식별에 반드시 정밀값이어야 하는 것은 아니다 → **연령대/생년 구간으로 대체 가능**한 후보다.

### 1-3. Claim 자동승인 로직 & 도달 시나리오 (P1-3)

`calculate_claim_confidence`(`claims.py:63-132`) 가중치:

| 신호 | 배점 | 근거 라인 | 위조 가능성(공개데이터 기준) |
|---|---|---|---|
| 이름 exact | 0.35 (부분 0.25 / 문자겹침 0.20) | 79-92 | **위조 쉬움** — `full_name`은 가입 폼 자유입력(`router.py:681`), 공개검색으로 피해자 실명 확보 |
| 출생연도 일치 | 0.25 | 94-100 | **위조 쉬움** — `birth_date`도 자유입력, 공개검색이 `birth_year` 반환 |
| 소속팀 일치 (exact) | 0.25 (부분 0.15) | 102-119 | **위조 가능** — `member.organization_id`가 가리키는 org명 == player.team_name. 공개검색이 team_name 반환, org-search로 동일 org 확보 후 프로필에서 연결 |
| 무기 데이터 존재 | 0.05 | 121-125 | player 행에 weapon 컬럼 있으면 자동 |
| 최근 대회 데이터 존재 | 0.05 | 127-131 | player 행에 last_competition_date 있으면 자동 |

임계값(`config.py:57-58`): 자동승인 `>= 0.85`, 수동검토 `0.50~0.85`, 자동거부 `< 0.50`.

**두 개의 진입 경로가 서로 다르게 동작한다 (정밀 구분):**

- **경로 A — 가입 시 자동 claim** (`_create_registration_claims`, `router.py:887-967`): 이 시점 `member`는 방금 insert된 행인데, `member_data`(라인 783-802)에 **`organization_id`가 없다**. 따라서 소속팀 0.25를 **못 받는다**. 최대 = 이름 0.35 + 생년 0.25 + (무기 0.05 + 최근 0.05) = **0.60~0.70 < 0.85** → **가입 폼만으로는 자동승인 불가**(pending으로 감). ✅ 현재 이 경로는 안전.
- **경로 B — 로그인 후 `/player-claim`** (`claims.py:201-339`): 인증된 회원이 호출. 이 회원이 **프로필에서 organization을 자기 소속으로 연결**해 `organization_id`를 세팅하고, 그 org명이 피해자 `team_name`과 같으면 → 이름 0.35 + 생년 0.25 + 소속 0.25 = **정확히 0.85 도달 → 자동승인** → `_link_player_to_member`(832-842)가 `members.player_id`를 피해자 선수로 연결, `verification_tier=3` 부여. **타인 프로필 탈취 성립.**

**핵심 결론:** 실제 탈취는 경로 B에서 성립하며, 재료(실명·생년·소속팀명) 3종이 **모두 무인증 공개검색(1-1)에서 나온다.** 즉 P1-2(과다 노출)와 P1-3(자동승인)은 결합 리스크다. 또한 `players` 테이블이 보유한 필드는 이름/소속/생년/무기로 **전부 공개 성질** — 서버가 대조에 쓸 수 있는 "비공개 비밀 신호"가 스키마상 존재하지 않는다(이는 아래 항목 6 옵션 B의 실현 가능성을 제약한다).

## 2. 항목 5 — 공개검색 재설계 옵션

공통 목표: (a) 호출 남용 차단(rate limit), (b) 응답 PII 최소화(특히 미성년), (c) 가입 UX 유지(사용자가 본인/자녀 후보를 식별해 선택할 수 있어야 함).

### 2-A. Rate limiting (세 옵션 공통 전제로 권장)

- **방식:** `slowapi`(Starlette 호환, `pip install slowapi`) IP 기반. `server.py`에 `Limiter(key_func=get_remote_address)` 등록 + 세 검색 엔드포인트에 `@limiter.limit(...)`.
- **주의:** Cloudflare Tunnel 뒤이므로 실제 클라이언트 IP는 `CF-Connecting-IP`/`X-Forwarded-For` 헤더에서 취득해야 함(직접 `remote_address`는 터널 내부 IP). key_func 커스터마이즈 필요.
- **임계값 제안:** 검색당 `20 requests / minute / IP` + `200 / hour / IP`. 정상 가입자는 몇 번의 검색으로 충분, 대량 스크레이핑은 차단.
- 이 rate limit은 아래 A/B/C 어느 필드 옵션과도 독립적으로 병행 적용 권장.

### 2-B. 응답 필드 옵션

| 옵션 | 반환 필드 변경 | 미성년 처리 | UX 영향 | 개인정보 보호 | 구현 난이도 |
|---|---|---|---|---|---|
| **옵션 A — 생년 구간화 + 소속 유지** | `birth_year`(정수) → `age_group`/`birth_decade`(예: "2010년대"·"중등부")로 대체. 이름·소속·무기·리그는 유지 | 미성년 후보는 이름을 부분마스킹(예: `홍*동`) + 소속만 표시 | 낮음 — 배지/소속으로 식별 가능, "YYYY년생" 정밀표시만 사라짐 | 중 — 정밀 생년(대조 재료 1개) 제거 | 낮음(프론트 라인 875만 조정) |
| **옵션 B — 로그인 사용자에게만 전체필드** | 비로그인: 이름+소속+연령대만. 로그인(가입 진행 중 세션): 전체 | 비로그인 응답에서 미성년 실명 부분마스킹 | 중 — 가입 흐름은 아직 미로그인 상태라 "먼저 이메일/OAuth 인증 후 검색" 순서로 위자드 재배치 필요 | 상 — 무인증 대량수집 원천 차단 | 중(위자드 단계 재정렬 + 세션 판정) |
| **옵션 C — 전면 마스킹** | 이름 `홍*동`, 소속 유지, 생년 구간화, `id`만 정확 | 전 연령 동일 마스킹 | 상 — 동명이인 구분 어려움, 본인 확신 저하로 오선택/이탈 ↑ | 상 | 낮음 |

**필드 옵션 상세 트레이드오프**
- 옵션 A는 P1-3의 대조 재료 중 "정밀 생년" 하나를 없애 자동승인 조합(이름+생년+소속=0.85)을 깨는 데 직접 기여한다. 소속을 남기므로 식별 UX는 거의 유지.
- 옵션 B는 노출 총량을 가장 크게 줄이지만(무인증 스크레이핑 불가), 가입 위자드에서 "인증 → 검색 → 선택" 순서 강제가 필요해 흐름 변경 폭이 크다. 현재는 검색이 먼저이고 인증이 뒤라 순서 역전.
- 옵션 C는 보호 강하지만 동명이인 많은 한국 성명 특성상 본인/자녀 식별 실패 위험이 커서 가입 전환율에 부정적.

## 3. 항목 6 — Claim 자동승인 재설계 옵션

전제: `players`는 전부 공개필드 → **공개데이터만으로 위조 불가능한 서버측 비밀 신호가 없다.** 따라서 "가중치 몇 개 더"로는 근본 차단이 어렵고, 신호는 (i) 자동승인 제거, (ii) 소유/실물 증명 도입, (iii) 문턱 상향 중 선택.

| 옵션 | 내용 | 무결성 효과 | 운영 부하 | 구현 난이도 |
|---|---|---|---|---|
| **옵션 A — 자동승인 완전 비활성화** | `/player-claim`도 항상 `pending`, 관리자 검토 필수(경로 A는 이미 사실상 pending). `CLAIM_AUTO_APPROVE_THRESHOLD`를 실질 무력화(예: 1.01) | **최고** — 공개데이터 조합만으론 절대 자동 링크 안 됨 | **높음** — 모든 선수연결을 사람이 검토 | **낮음** — 임계값 상수 + 분기 |
| **옵션 B — 소유/실물 증명 신호 추가** | 이미 존재하는 Gemini 사진 인증(마스크/도복+이름·날짜 종이, `config.py:74-106`, `GeminiVerifier`)을 고배점(예: 0.40) 신호로 편입. 공개 3필드(이름·생년·소속) 합계 상한을 0.85 미만(예: 0.80)으로 재배분 → 사진 없이는 자동승인 불가 | **높음** — 위조하려면 실물 사진 필요(공개데이터로 불가). 미성년은 별도 정책 | 중 — 사진 있는 건만 자동, 없으면 pending | **중~상** — claim 흐름에 사진 인증 연동, 가중치 재설계 |
| **옵션 C — 임계값 상향** | `CLAIM_AUTO_APPROVE_THRESHOLD` 0.85 → 0.95 등 | **낮음** — 이름 exact+생년+소속 재배점만으로도 다시 도달 가능, 위조 재료가 여전히 공개 | 낮음 | **낮음** — 상수 1줄 |

**옵션별 상세**
- **A**: 가장 안전하고 구현 단순. 운영자가 늘어나는 검토 큐를 감당해야 함. 현재 가입자 수(초기 단계)에선 부하가 낮아 현실적. AI 리포트(`AIVerificationReporter`)로 검토 보조 가능.
- **B**: 근본적. players에 비밀 신호가 없다는 제약을 "실물 소유 증명"으로 우회하는 유일한 자동화 경로. 단 사진 인증 UX·저장(개인정보)·미성년 예외를 함께 설계해야 하고, 제0원칙 4번(서류 수집 금지)과 충돌하지 않도록 마스크/도복 사진 방식(신분증 아님)을 유지해야 함.
- **C**: 겉보기 방어일 뿐. 가중치 재배분으로 쉽게 재도달 → **권장하지 않음.**

## 4. 권장안 (최종 결정은 사용자)

| 항목 | 권장 옵션 | 이유 |
|---|---|---|
| 항목 5 rate limit | **2-A 적용(20/min, 200/hr, CF 헤더 기반 IP)** | 남용/스크레이핑 차단은 필드옵션과 무관하게 필수. 저비용 고효과 |
| 항목 5 응답필드 | **옵션 A(생년 구간화 + 미성년 이름 부분마스킹, 소속 유지)** | P1-3 대조재료(정밀 생년)를 없애면서 가입 식별 UX를 거의 보존. 옵션 B는 위자드 재설계 부담, 옵션 C는 전환율 훼손 |
| 항목 6 자동승인 | **1순위 옵션 A(자동승인 비활성화)**, 중기적으로 **옵션 B(사진 소유증명) 병행** | 초기 단계 운영부하가 낮아 A로 즉시 리스크 제거, 규모 확장 시 B로 자동화 복원. C는 방어력이 낮아 제외 |

**결합 효과:** 항목 5 옵션 A로 정밀 생년을 없애면 경로 B 자동승인 공식(이름 0.35+생년 0.25+소속 0.25=0.85)에서 생년 0.25가 빠져 0.60으로 떨어진다. 여기에 항목 6 옵션 A(자동승인 off)를 더하면 **이중 방어**가 된다. 둘 중 하나만 골라도 P1-3은 차단되지만, 공개 노출(P1-2) 자체를 줄이는 항목 5도 독립 가치가 있으므로 둘 다 권장.

> ⚠️ 미성년 이름 마스킹/사진 인증은 개인정보·아동보호가 얽혀 있어, 정책 확정 시 제0원칙 4번(서류 수집 금지)과 반드시 재대조 필요.

## 5. 구현 시 영향 파일 & 검증 방법

**항목 5 (rate limit + 필드):**
- `services/account/app/server.py` — `slowapi` Limiter 등록, CF 헤더 key_func, exception handler.
- `services/account/app/auth/router.py` — 세 엔드포인트에 `@limiter.limit`, SELECT/응답 가공(생년 구간화·미성년 마스킹)을 `_annotate_and_filter_by_weapon_league` 근처에 추가.
- `services/account/templates/auth/register.html` — 라인 875 "YYYY년생" 표시를 연령대/구간 표시로 교체(응답 키 변경 시). `leagues` 기반 게이팅(811-813)은 유지.
- `requirements`(account) — `slowapi` 추가 (ARM64: `arch -arm64 python3 -m pip install slowapi`).

**항목 6 (자동승인):**
- `services/account/app/config.py:57` — `CLAIM_AUTO_APPROVE_THRESHOLD` 조정(옵션 A: 무력화, 옵션 C: 상향).
- `services/account/app/verification/claims.py:277-287` 및 `auth/router.py:915-922` — 자동승인 분기(두 곳 동일 로직) 수정. **두 파일 모두** 고쳐야 일관성 유지.
- 옵션 B 선택 시: `verification/processor.py`(GeminiVerifier)·claim 흐름에 사진 인증 연동, `calculate_claim_confidence` 가중치 재설계.

**검증 방법:**
- **단위테스트:** `calculate_claim_confidence`에 대해 (이름+생년+소속) 조합이 임계값에 도달/미달하는지 케이스별 assert. 옵션 A는 "어떤 입력도 approved를 만들지 않음" 테스트.
- **curl (account 서버 port 70):**
  - `curl "http://localhost:70/auth/public/player-search?name=홍길동"` → 응답에 정밀 birth_year가 없고 구간/연령대만 있는지, 미성년 이름 마스킹 확인.
  - rate limit: 동일 IP로 21회 연속 호출 시 429 반환 확인.
  - claim 자동승인: 실명·생년·소속을 맞춘 요청이 `pending`으로 떨어지는지(옵션 A) 확인.
- **회귀:** 정상 가입 흐름(선수 검색→선택→가입)이 여전히 동작하는지 브라우저 확인.
