## 검증 규칙 레퍼런스 (R1 ~ R28)

### 이벤트 레벨 검증 (R1 ~ R6, R14 ~ R17, R22 ~ R28)

| 규칙 | 이름 | 심각도 | 설명 |
|------|------|--------|------|
| **R1a** | Self-bout | ERROR | `player1 == player2` — 빈 슬롯에 복제된 팬텀. **raw bout 을 직접 본다** (CASE-008) |
| **R1b** | Duplicate bout | ERROR | 동일 선수쌍 + 동일 라운드에 2회 이상 등장 |
| **R1c** | Phantom capacity | ERROR | 한 라운드의 실제 경기 수 > 브래킷 정원 (16강 최대 8). 부전승 제외 |
| **R2** | Winner inconsistency | ERROR | `winner_name`이 `player1`도 `player2`도 아님 |
| **R3** | Score anomaly | ERROR/WARN | 음수 점수, DE > 15점(개인)/45점(단체), 동점+승자 존재 |
| **R4** | Invalid round_name | ERROR/WARN | 빈 라운드명 또는 비표준 라운드명 |
| **R5** | Bracket topology | WARNING | round N 승자가 round N+1 참가자에 없음 |
| **R6** | Ranking mismatch | ERROR/WARN | `final_rankings` 1~2위와 DE bracket 결과 불일치 |
| **R26** | Final ranking structure | ERROR | 최종순위에 1위/2위가 없거나 둘 이상 (동률은 3위만 허용 — FIE) |
| **R27** | Final ranking roster | WARNING | 최종순위에만 있고 풀·DE·참가자 명단에 없는 이름. `(*)` 정규화 필수 (CASE-010) |
| **R28** | DE name collapse | ERROR/WARN | 한 이름이 DE 슬롯 10개 이상 점유 (구조적 상한 9). 내용 중복=ERROR, 동명이인 가능=WARNING |

### 선수 레벨 검증 (R7 ~ R13, R19 ~ R21)

| 규칙 | 이름 | 심각도 | 설명 |
|------|------|--------|------|
| **R7** | Same-round duplicate | ERROR/WARN | 한 이벤트 내 동일 라운드 2경기 이상 (dual_de는 독립 검증). 내용 중복 또는 소속 1곳=ERROR, 순위표에 소속 2곳 이상=WARNING(동명이인 설명 가능) |
| **R8** | Round progression | ERROR | 이긴 라운드의 **그 브래킷에 실재하는** 다음 라운드에 선수가 없음 = 경기 유실. 부전승은 출전으로 인정, `winner_name` 없으면 점수로 추론 (라운드를 뭉쳐 비교하던 오탐 3,488건 제거 — CASE-009) |
| **R9** | Pool bout count | WARNING | 한 이벤트 pool 경기수 > 8 (보통 4~7) |
| **R10** | Gender inconsistency | ERROR | 동일 선수가 남/여 종목 동시 출전 → 동명이인 오염 |
| **R11** | Age group regression | ERROR | 나이그룹 역행 (일반부 → 고등부 등) → 동명이인 가능성 |
| **R12** | Weapon count | WARNING | 무기 3종 이상 사용 → 동명이인 의심 |

### 🔴 검증 범위 — Guardian 은 전수가 아니다

**두 경로의 숫자를 나란히 놓고 비교하지 말 것.** 보는 대상이 다르다.
(2026-09-28 에 실제로 한 번 오해가 났다 — Guardian 리포트 문구가 "전체 데이터 검증" 이었다.)

| 경로 | 범위 | 소요 | 언제 도는가 |
|------|------|------|------------|
| `DataGuardian.daily_health_check()` | **최근 대회 20개** (`DAILY_SCAN_LIMIT`) | 수십 초 | 스케줄러 일일 |
| `DataGuardian.post_scrape_validation()` | 대회 1개 지정 시 그 대회, 아니면 **최근 50개** | 수십 초 | 스크래핑 직후 |
| `DataGuardian.run_full_validation()` | **최근 50개** (`DEFAULT_SCAN_LIMIT`) — 이름과 달리 전수 아님 | 수 분 | 수동 |
| `scripts/run_validation.py` | **전 연도 전수** (대회 124개 / 종목 2,968개) | **약 14분** | 수동 배치 |

전체 대회는 148개이므로 Guardian 기본값(50)으로도 전체의 1/3 만 본다.
Guardian 의 결과 dict 와 로그·Discord 문구에는 `scope` 가 실려 나간다
(`"최근 대회 20개 / 종목 NNN개"`). 범위 상수는 `app/data_guardian.py` 모듈 상단에 있다.

**전수 배치를 돌리는 방법** (운영 서버의 이벤트 루프를 14분 점유하므로 서버 안에서 돌리지 않는다):

```bash
cd services/data
# DB 왕복 없이 반복 실행하려면 이벤트 덤프를 캐시에 둔다
PYTHONPATH=".:../../packages" python scripts/run_validation.py --cache /tmp/ev.pkl
# 특정 규칙 표본 열어보기 (트리아지)
PYTHONPATH=".:../../packages" python scripts/run_validation.py --cache /tmp/ev.pkl --rule R8 --sample 10
# Guardian 범위 재현 (숫자 대조용)
PYTHONPATH=".:../../packages" python scripts/run_validation.py --cache /tmp/ev.pkl --limit-comps 20
```
이슈 전량은 `logs/validation_issues.json` 에 저장된다 (`--out` 으로 변경).
최종순위 전용 감사는 별도다: `python scripts/audit_final_rankings.py` → `logs/audit_final_rankings.json`.

> **정기 실행은 아직 자동화돼 있지 않다.** 전수 배치를 도는 cron/launchd 항목은 없다.
> 재수집 작업 뒤에는 사람이 위 명령을 돌려 ERROR 추이를 확인해야 한다.

## 발견된 오류 사례 (Discovered Cases)

### CASE-001: Self-bout (tournament_table 파싱 버그)

| 항목 | 내용 |
|------|------|
| **규칙** | R1a |
| **발견일** | 2025-12 |
| **상태** | ✅ 수정 완료 |
| **심각도** | ERROR |
| **영향 범위** | tournament_table 형식의 DE bracket |
| **근본 원인** | `de_scraper_v4.py`의 `_parse_tournament_table_bracket()`에서 빈 슬롯 또는 부전승 시 같은 선수를 양쪽에 배치 |
| **증상** | full_bouts에 `player1_name == player2_name`인 bout 존재 |
| **수정 내역** | 1) 스크래퍼에서 self-bout 생성 방지 로직 추가 2) `data_validator.py`의 `_get_full_bouts_from_bracket()` 3개 경로 모두에 런타임 필터 (Path 1: full_bouts, Path 2: _reconstruct_bouts_from_duplicated_bbr, Path 3: bouts_by_round) |
| **검증** | R1a 이슈 0건 확인 (2026-02-26 재검증 완료) |
| **🔴 상태 정정 (2026-09-28)** | **이 케이스는 해결된 것이 아니었다. → CASE-008 참조.** 위 "런타임 필터"는 검증기의 **입력에서 증거를 지운 것**이고, DB 의 오염 레코드는 그대로 남았다. 그래서 R1a 가 0건이 됐다 — 데이터가 깨끗해져서가 아니라 **규칙이 눈을 감았기 때문**이다. 2026-09-28 실측: DB 에 self-bout 1,218경기 / 89종목이 잔존. |

### CASE-002: full_bouts 라운드명 오배정 (bracket_size 불일치)

| 항목 | 내용 |
|------|------|
| **규칙** | R7 |
| **발견일** | 2025-12 |
| **상태** | ✅ 수정 완료 |

### CASE-008: 빈 슬롯에 복제된 팬텀 경기 — 한 이름이 브래킷을 덮는다

| 항목 | 내용 |
|------|------|
| **규칙** | R1a (self-bout) · R1c (정원 초과) · R28 (이름 뭉개짐) · R27 (순위표까지 전이) |
| **발견일** | 2026-09 (2025-12 CASE-001 의 미해결 잔량이 실체로 확인됨) |
| **상태** | ⚠️ 발견 — 탐지 구현 완료, 데이터 복구 미착수 |
| **심각도** | ERROR |
| **영향 범위** | 89종목 / self-bout 1,218경기 (2026-09-28 스냅샷). 연도별 2019:158 · 2020:61 · 2021:164 · 2022:814 · 2025:21 |
| **근본 원인** | DE 브래킷의 **빈 슬롯**(참가자가 브래킷 크기보다 적어 남는 자리)에 직전 파싱의 잔류 이름과 직전 경기의 점수가 그대로 채워진다. 실측에서 **전수 1,218경기의 self-bout 이름이 단 하나('정효정')** 였다 — 특정 대회의 특성이 아니라 파서의 상태가 종목 사이에 새는 구조적 버그다 |
| **증상** | ① `player1_name == player2_name` ② 라운드의 실제 경기 수가 브래킷 정원을 초과 (16강 16경기 > 정원 8) ③ 한 이름이 DE 슬롯 70개 이상 점유 ④ 점수까지 동일하게 복제 (예: 전부 15-1) ⑤ 드물게 그 이름이 `final_rankings` 1위까지 올라간다 |
| **실측 예 (event id 1440)** | 2022 제10회 대한펜싱협회장배 고등부 여자 플러레(개). 최종순위 7명 = 실제 참가자 7명. `bracket_size` 32 → 32강 슬롯 16개 중 4개만 실경기, 나머지 12개가 `정효정 vs 정효정 15-1`. 16강·8강·결승도 같은 방식으로 부풀려져 총 46 bout |
| **탐지 방법** | `PYTHONPATH=".:../../packages" python scripts/run_validation.py` → R1a / R1c / R28. 감사 쪽은 `scripts/audit_final_rankings.py` 의 F12(CHAMPION_MISMATCH) 로도 일부 드러난다 |
| **왜 이제서야 잡혔나** | CASE-001 이 R1a 를 **검증기 입력에서 필터링**해 해결로 표기했다. `_get_full_bouts_from_bracket()` 이 세 경로 모두에서 `p1 == p2` 를 버리므로 R1a 가 받는 목록에는 self-bout 이 **한 건도 없다.** 규칙은 존재했지만 구조적으로 발동 불가였다. 2026-09-28 에 R1a/R1c/R28 을 raw bout 을 보는 경로로 옮겨 해결 |

### CASE-009: R8 라운드 진행 보존법칙 — 규칙 자체의 산술 오류 (오탐 3,488건)

| 항목 | 내용 |
|------|------|
| **규칙** | R8 |
| **발견일** | 2026-09 |
| **상태** | ✅ 수정 완료 (규칙 수정. **데이터 문제가 아니었다**) |
| **심각도** | ERROR 로 보고되던 것이 전부 정상 데이터 |
| **영향 범위** | 전 연도 전수 검증의 R8 ERROR 3,488건 = 전체 ERROR 4,888건의 71% |
| **근본 원인** | R8 이 라운드를 `CATEGORY_ORDER` 5칸으로 **뭉쳐서** 비교했다. `get_round_category()` 는 256강·128강·64강·32강을 모두 `t32_and_below` 한 칸에 넣는다. 따라서 64강과 32강을 연달아 이기고 16강을 한 번 치른 **완전히 정상인 선수**가 `t32_and_below 승리 2회 > 16강 출전 1회` 로 "1경기 유실" 판정을 받았다 |

## CASE-017: 분리된 프로필이 같은 id 로 덮어써져 기록이 사라짐 (2026-09-30)

**증상** — 수집 307,593건 중 **7,489건(172개 이름)이 어느 프로필에도 들어가지 않았다.**
김하은은 493건 중 331건(67%)이 유실돼 프로필에 162건만 남아 있었다.

**원인** — `_generate_player_id()` 가 (이름, 첫 소속)만으로 id 를 만든다. 분리 과정이 한 사람의

id 가 나오고 `self.profiles[id] = profile` 이 앞 프로필을 통째로 교체했다.

**처리** — `_attach_profile()` 로 **덮어쓰지 않고 합친다**. 단 성별이 다르면 합치지 않고 성별
꼬리표를 붙인 별도 id 를 만든다(제1원칙: 성별 불변). 나이그룹이 내려가는 프로필은 분리 후
최종 단계(`_enforce_age_monotonicity()`)에서 가른다 — 분리 경로가 여러 갈래라 한 곳에 규칙을
넣으면 다른 경로로 들어온 레코드가 그대로 남는다.
